# Архитектура

Репозиторий представляет собой TypeScript-монорепозиторий. API построен на NestJS и Fastify; будущие админ-панель диспетчера и мобильное приложение водителя будут находиться в отдельных директориях `apps/` и использовать его публичный API.

## Границы API

- **HTTP controllers** валидируют входные данные и предоставляют транспортные контракты.
- **Application services** реализуют сценарии использования.
- **Infrastructure repositories** сохраняют доменные сущности через Prisma.
- **Domain types** по возможности не зависят от NestJS и Prisma.

PostgreSQL — источник истины для операционных данных. Redis зарезервирован для фоновых задач, например OCR/AI-извлечения данных из Rate Confirmation. Оригинальные файлы RC хранятся в S3-совместимом object storage, а не в Git или базе данных.

После загрузки RC API сохраняет `DocumentExtraction` со статусом `PENDING` и добавляет job в очередь BullMQ. Отдельный процесс `worker:dev` читает документ из object storage, переводит статус в `PROCESSING`, вызывает выбранный AI provider и сохраняет структурированный результат с confidence для каждого поля. При ошибке worker сохраняет `FAILED` и текст ошибки; BullMQ повторяет задачу до трёх раз.

AI provider является портом приложения. Сейчас доступны безопасный локальный `mock` и `gemini`. Gemini получает только байты конкретного документа и инструкцию извлечения; API-ключ передаётся заголовком запроса из переменной окружения и не сохраняется в базе данных или логах приложения. Извлечённые значения не меняют Load автоматически: диспетчер должен просмотреть и подтвердить их в следующем сценарии.

## Граница данных водителя

Финансовые и внутренние данные диспетчера никогда не должны возвращаться из endpoints для водителя. `LoadFieldVisibility` — начальный механизм хранения настройки видимости отдельных полей; соблюдение этого правила обеспечит отдельный endpoint-проекция для приложения водителя.
